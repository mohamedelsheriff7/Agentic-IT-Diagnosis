The main focus of this project is diagnosis. We are not building an agent that just reads a ticket, classifies it, and predicts a resolver group. The agent should investigate the reported issue, identify possible causes, ask the right diagnostic questions, gather evidence, rule out alternatives, and reach a defensible diagnosis before deciding whether to resolve, route, or escalate.
1) BACKGROUND:
A big part of the misrouting problem is that tickets describe symptoms, not the actual problem. For example, "I cannot access the application" could be caused by any of these:
An expired or forgotten password
An account lockout
An MFA issue
A missing entitlement
An application authentication problem
A network issue
A wider outage
Classifying the ticket on its first sentence sends it to the wrong team. A good support agent investigates first.
Your job is to build a working prototype of the core of that solution. We will use a ticket model aligned with IBM Control Desk / IBM Maximo IT and entirely synthetic data.
2) OBJECTIVE:
Build an agentic solution that takes a new IT ticket and can:
a) Diagnose: Understand the reported symptoms, identify plausible causes, detect missing information, and ask targeted questions that distinguish between competing diagnoses.
b) Gather evidence: Use the user's answers, ticket information, troubleshooting knowledge, similar historical tickets, and available tools to narrow down the possible causes.
c) Resolve: When an approved knowledge article has a safe, verified fix and all required conditions are met, guide the user through the fix, confirm it worked, and record the resolution on the ticket.
d) Route: When specialist support is needed, assign the ticket to the correct resolver group based on the diagnosis and its evidence, not the original ticket wording. Include a confidence level and a clear reason.
e) Escalate: Recognize security-sensitive cases, cases that require a human, and patterns that indicate a wider incident or outage. For outages, create a global ticket, link the related tickets, and notify the right group.
The target diagnostic flow is:
Symptoms → Candidate Diagnoses → Diagnostic Questions → Evidence → Eliminate Alternatives → Diagnosis → Resolve / Route / Escalate
3) TECHNICAL ARCHITECTURE:
The solution must be designed for portability. The goal is a diagnostic agent that can later be published and reused outside this project, for example on the IBM Agent Connect catalogue, so it must not be tightly tied to one platform.
Diagnostic Agent (Python):
Built as an independently deployable Python agent/service.
Owns all diagnostic logic: conversation state and context, generating candidate diagnoses, choosing the next question or check, collecting evidence, eliminating unsupported diagnoses, knowledge retrieval, similar-ticket analysis, evidence-based confidence, and safety/human-escalation rules.
Exposed through a supported agent interface and connected to watsonx Orchestrate as an external agent. Check the Orchestrate documentation for the supported external-agent options.
A stateful Python agent framework such as LangGraph may be used, but you must justify the choice.
watsonx Orchestrate:
Acts as the orchestration layer where the full solution is integrated and demonstrated.
Coordinates the Diagnostic Agent with ticket tools, routing, escalation, human-in-the-loop steps, and the other collaborator agents.
Intended structure:
watsonx Orchestrate → IT Support Supervisor agent.
The Supervisor coordinates three collaborator agents: the Diagnostic Agent (external, Python), the Routing agent, and the Escalation & Outage agent.
The Diagnostic Agent uses the knowledge base, similar-ticket search, and diagnostic tools.
All tools read from and write to the mock Maximo IT API.
Key principle: the Diagnostic Agent must be testable on its own, without Orchestrate. Orchestrate is where everything comes together; it is not where the diagnostic logic lives.

PHASE 2: SYNTHETIC DATA (Week 1, Days 3–5, Workstream A)
Taxonomy:
Use three levels: Domain > Category > Subcategory / Diagnosis.
Domains and target shares: Access Management (~40%), Application (~35%), Endpoint (~10%), Network/Other (~15%).
Aim for 20 to 30 meaningful diagnostic categories.
Resolver groups (6 to 8). Examples:
Service Desk L1
IAM Team
Application Support
Endpoint Support
Network Operations
Security Operations
Servers & Infrastructure
Datasets:
Historical resolved tickets: 400 to 600. Each should include symptoms, troubleshooting worklogs, the final diagnosis, the resolver group, and the resolution. These feed the knowledge base and the similar-ticket search.
Test set: 80 to 100 new, open tickets with hidden ground truth. For each ticket, label:
The correct category and the actual diagnosis.
The information available in the ticket at the start.
The information the agent can only discover by asking questions.
The correct resolver group.
Agent-resolvable (Y/N), human intervention required (Y/N), and escalation (Y/N).
Ambiguous cases: deliberately include tickets whose initial symptoms could match several diagnoses, so the agent has to ask questions to tell them apart.
Outage scenarios: 3 clusters. Example: 20 VPN tickets from the same site within 30 minutes.
Decoy scenarios: 3 cases where many tickets share a category but are spread over days or different sites. These must NOT trigger escalation.
Realism requirements:
Mix English, Arabic, and Franco-Arabic. Include typos, vague descriptions ("system not working"), and missing fields.
About 15% of historical tickets should be misrouted first and then reassigned, with the reassignment visible in the worklog. This mirrors the client's real misrouting rate.
Include security-related tickets, a realistic spread of priorities, and some fake sensitive content (fake passwords, fake IPs) to test how the agent handles it.
Format and generation:
JSON is the source of truth, with CSV exports where useful.
Document the schema with a field-by-field mapping to Maximo IT fields.
Generate the data with a Python script using a fixed random seed so it can be reproduced. You may use an LLM to write ticket descriptions, but the script controls the schema and the labels.
Important: the test set must be written separately from the knowledge base, using different generation prompts or a different author. Otherwise the agent will just be matching its own wording, and the results will look better than they are.
Deliverables (end of Week 1):
Schema document with the Maximo field mapping.
The historical dataset.
The diagnostic test set.
A short data profile: counts per domain, group, and language.

The questions must be designed to tell competing diagnoses apart, not just to collect more information. A good question removes at least one candidate diagnosis whatever the answer.

Which group owns what.
Clear boundaries between overlapping groups. Example: a password reset goes to IAM, unless the account was locked by a security policy, in which case it goes to Security Operations.
c) Escalation and outage policy:
Thresholds, for example N or more tickets on the same configuration item, category, or location within T minutes.
Severity levels and who gets notified at each level.
What always goes to a human, regardless of confidence: security issues, privileged access, and critical priority.

Start the articles from the diagnostic taxonomy on Day 3. Refine them with the historical synthetic tickets once those are ready.
Test retrieval with at least 15 representative scenarios, and improve the article structure until the right article comes back.

PHASE 4: MOCK BACKEND & TOOLS (Week 1 Day 3 through Week 2, Workstream C)
We don't have a Maximo IT instance, so build a small mock of the Maximo IT ticket API (for example, FastAPI with SQLite), loaded with the synthetic data and published with an OpenAPI spec. The tools must be usable both by the Python Diagnostic Agent and by the Orchestrate agents.
Minimum tools:
Get Ticket Details: Retrieves a ticket's full record and worklogs using its ticket ID.
Search Similar Tickets: Finds the most similar resolved historical tickets to a given ticket description. Simple keyword search is fine.
Assign Ticket: Assigns a ticket to a resolver group and records the confidence level and the reason for the choice.
Add Worklog Entry: Adds a note to a ticket's worklog describing what the agent did and why.
Resolve Ticket: Marks a ticket as resolved and records the resolution steps and the knowledge article used.
Count Recent Tickets: Counts tickets that share a category, configuration item, or location within a given time window. Used for outage detection.
Find Open Global Tickets: Checks whether an open global ticket already exists for a given category, configuration item, or location.
Create Global Ticket: Creates a global ticket for a repeated issue or outage, with a summary, severity, and the related tickets.
Link Ticket to Global Ticket: Links a new ticket to an existing global ticket so it is tracked as part of the same issue.
Add other diagnostic tools if they clearly help the agent gather evidence. Examples: a simulated account status check, or a service health check.
To stay on schedule, start the mock API with a small hand-made sample of tickets on Day 3. Switch to the full dataset once Workstream A delivers it.
Deliverables (mid-Week 2):
The running mock API and its OpenAPI spec.
Each tool tested on its own.
PHASE 5: DIAGNOSTIC AGENT & ORCHESTRATION (Week 2, Workstream D, everyone contributes)
Diagnostic Agent (Python). For each ticket, the agent should:
Understand the reported symptoms.
Retrieve the relevant diagnostic knowledge.
Generate a shortlist of plausible diagnoses.
Identify what evidence is missing.
Choose the most useful next question or check.
Add the new evidence.
Eliminate diagnoses the evidence doesn't support.
Repeat as needed.
Reach a diagnosis when there is enough evidence, or explicitly decide that a human needs to investigate.
Return a structured result: diagnosis, evidence, confidence, recommended action (resolve / route / escalate), and rationale.
If the recommended action is to resolve, and the knowledge article marks the issue as resolvable by agent with its conditions met, the agent walks the user through the fix, confirms it worked, and resolves the ticket with a reference to the article.
The agent must keep its diagnostic state, so we can see not only the final answer but how it got there. Example trace:
Initial candidates: password expired, account locked, MFA failure, missing application entitlement.
Question: "Can you access other corporate applications?"
Evidence: Yes.
Eliminated: general account/password issue.
Remaining: MFA/application authentication issue, missing entitlement.
Next step: ...
Orchestrate agents:
IT Support Supervisor agent: the entry point. It receives a ticket by ID, or a user describing an issue in chat, and coordinates the collaborator agents.
Diagnostic Agent: the external Python agent described above, connected as a collaborator.
Routing agent. When the diagnosis requires a specialist:
Picks the owner group based on the diagnosis and its evidence, plus a confidence level (High / Medium / Low), the top 3 alternative groups, and a reason.
High confidence: assign directly.
Medium confidence: assign to L1 triage with the recommendation attached.
Low confidence: send to human triage.
Security, privileged access, and critical tickets always go to a human, whatever the confidence.
Escalation & Outage agent. Runs on every new ticket:
First, check for an open global ticket. If one exists, link the new ticket to it and tell the user it's a known issue instead of re-diagnosing.
Otherwise, check recent ticket counts. If a threshold is met, create a global ticket, link the related tickets, and notify the owner group.
About confidence: an LLM's self-reported confidence is not reliable. Base the confidence level on evidence you can check:
The strength of the knowledge base match.
Whether the required information is complete.
How many similar historical tickets reached the same diagnosis and group.
Whether competing diagnoses have been ruled out.
Write this rule explicitly in the agent instructions and in the documentation.
Every action must write a worklog entry stating what was decided, the supporting evidence, and which knowledge article or historical tickets were used. These logs must also be stored in a database so we can review the agents' actions and find issues.
Start building early in Week 2 against the sample data and early tools. Don't wait for every other workstream to finish.
